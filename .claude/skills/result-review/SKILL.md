# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | ★【規則書】報廢越多清潔費越高（超過 5 份每份 3 元，16 份以上另加 50 元）。【推測】備貨超過實際需求，或這樣菜客人不想買，要先看盤點是「賣出 0」還是「只賣出一部分」 | ★先到盤點頁找報廢最多的菜，把備貨降到「賣出 ＋ 沒買到」（可用 reorder-check）。賣出是 0 的菜，先確認客人有沒有人想吃，沒有人想吃再考慮不上架（推測，要用下一版試算驗證） |
| 嫌太貴很多 | ★【觀察】客人剩下的預算比定價低，所以不買（規則書：價格 ≤ 剩下預算才買）。【推測】定價高於這群客人的預算，或客人先買了別樣、剩下預算不夠 | ★只對「嫌太貴」的那一樣菜小幅降價（在可定價範圍內，一次一樣、一次一小步），並注意單份收益會變少；降完要重跑試算，看多賣的份數有沒有補回差額 |
| 想吃的沒上架很多 | ★【觀察】客人想吃的菜今天沒賣。【推測】上架的組合和這群客人想吃的不一致（每天最多上架 4 樣） | ★找出被想吃最多、卻沒上架的菜，用它換掉賣得最差的一樣（一次最多換 1 樣），並同步調整備貨與合計份數（不能超過 80） |
| 因為討厭的菜不進門 | ★【規則書】客人討厭的菜有上架，他就整個人不進門，也不留評價。【推測】某樣菜為了少數人，反而擋掉了更多客人 | ★比較「討厭它的客人數」和「那樣菜賣出的份數」。擋掉的客人比賣出的還多，才考慮不上架那樣菜（一次只動一樣，並重跑試算確認） |
| 星等往下掉 | ★【規則書】滿意 < 30% 或不滿 ≥ 25%，星等會下降；「不滿」是什麼都沒買到；「滿意」要買到最想吃的、價格不超過建議售價。【推測】多半是賣完、太貴或沒上架造成不滿太多，或定價高於建議售價拿不到滿意 | ★先看「沒買到的客人」哪一類最多，優先處理那一類；想拉高星等，可先把價格調回建議售價以內（注意單份收益）。星等會影響隔天來客數，所以要連同隔天一起看 |
| ★ 我自己發現的現象：宣傳後增加來客，但淨利未改善 | ★【先核對這三項，再下結論】新增收入 ＝ 宣傳後收入 − 宣傳前收入；新增成本 ＝ 多備貨的成本 ＋ 多出來的報廢清潔費；再扣掉宣傳費。「新增收入 − 新增成本 − 宣傳費」≤ 0，代表宣傳沒回本。【推測】來客變多，但多出的客人沒買到（賣完、太貴、沒上架），或多備的貨變成報廢，或新增的客人偏向低價菜 | ★先算出上面三項數字，再決定調整：新增收入小於宣傳費，就降低宣傳費或不宣傳（規則書：200 元客人 +20%、500 元 +45%）；多出的客人沒買到，先補備貨（reorder-check）再宣傳；報廢變多，先調回備貨。一次只改一項，用下一版試算比較 |

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
